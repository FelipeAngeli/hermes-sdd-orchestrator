# Executors

Project-owned file. It selects, per stage, which external CLI runs the worker, which model it uses, and its hard timeout. Edit the JSON block below to change executors; never edit `.hermes.md`, `LOOP_POLICY.md` or a command line for that. `runtime/executor_launch.py` is the only reader, and it is the only way to dispatch a worker.

```json
{
  "executors_version": 1,
  "stages": {
    "SPECIFY":   {"executor": "claude", "model": null, "timeout_seconds": 600, "max_turns": 40},
    "CLARIFY":   {"executor": "claude", "model": null, "timeout_seconds": 600, "max_turns": 40},
    "PLAN":      {"executor": "claude", "model": null, "timeout_seconds": 900, "max_turns": 60},
    "TASKS":     {"executor": "codex",  "model": null, "timeout_seconds": 600, "max_turns": null},
    "IMPLEMENT": {"executor": "codex",  "model": null, "timeout_seconds": 900, "max_turns": null},
    "TEST":      {"executor": "codex",  "model": null, "timeout_seconds": 600, "max_turns": null},
    "REVIEW":    {"executor": "claude", "model": null, "timeout_seconds": 600, "max_turns": 40}
  }
}
```

## Fields

- `executor`: `claude` or `codex`.
- `model`: `null` uses the CLI's configured default; otherwise a plain model name passed as `--model`.
- `timeout_seconds`: hard wall-clock limit in seconds, 1–7200. On expiry the launcher kills the whole process group and records exit code `124`.
- `max_turns`: Claude only (`--max-turns`); `null` leaves the CLI default. Codex ignores it.
- Optional `tools` (Claude `--tools`; default `Read,Grep,Glob`), `permission_mode` (Claude `--permission-mode`) and `sandbox` (Codex `read-only` or `workspace-write`; default `workspace-write` for IMPLEMENT and TEST, `read-only` otherwise).
- Optional top-level `allow_bypass_permissions` (default `false`). A stage with `permission_mode: "bypassPermissions"` is refused with `EXECUTOR_POLICY_UNSAFE` unless the owner sets `"allow_bypass_permissions": true` next to `executors_version`, accepting that the worker then runs every tool without a check.

A stage omitted from `stages` keeps the default shown above. A missing file means the same defaults. An invalid block returns `POLICY_INVALID` and nothing is dispatched.

## Trust and isolation

Whoever can edit this file chooses the program that runs, its permissions and its model, so treat it like code: only the project owner edits it, and the installer reports its SHA-256 for review. `sdd.py start` pins that SHA-256 (together with `GATES.md`) in `delivery.controller_policies`, and every `sdd.py gate` re-verifies both: a file that changed mid-demand stops the loop with `CONTROLLER_POLICY_CHANGED_DURING_DEMAND` until the user re-confirms it with `sdd.py confirm-policy --name executors --quote '<their words>'`.

**A writing worker never shares a filesystem with the controller.** A worker that can write the repository can rewrite everything the controller keeps there — this file, `GATES.md` (whose commands run on the host, outside every sandbox), `runtime/*.py`, the stage briefs, STATE and the journal — *and* every hash those would be checked against, because each anchor lives in that same writable tree. A worker that edits a file and its anchor in one step leaves nothing to detect, so detection is not the boundary here: the dispatch is refused. With the controller inside the repository (`--local-storage`), a writing stage (IMPLEMENT, TEST) stops with `CONTROLLER_WRITABLE_BY_WORKER` and is never dispatched, also when the action was already PREPARED. The criterion is the controller's physical location inside the repository (a device/inode ancestor walk), not the storage label. `migrate_to_vault.py` is not the exit: it moves STATE and the journal but keeps `runtime/*.py` and `policies/` in the repository by design. The exit is to abandon the demand (`sdd.py abandon`), reinstall the controller in Obsidian mode with `install_project.py --obsidian-vault <vault>` (its container is never a writable root for a worker), then start again; the stop prints these steps as `exit_commands`, including moving the old in-repository controller into `<vault>/<project>/.hermes-local-controller-backup/` and confirming the new container's policies. Read-only stages (SPECIFY, CLARIFY, PLAN, TASKS, REVIEW) keep running meanwhile, since a worker that cannot write cannot rewrite the controller. Obsidian storage is the only configuration that runs a writing worker at all.

The checks below stay as defence in depth — they catch the accident, a careless edit and anything that reaches these files outside a dispatch — but they are no longer what stands between a hostile writing worker and the host.

- A writing worker (Codex with `workspace-write`, or Claude with any tool other than `Read`, `Grep`, `Glob`, `LS`, `NotebookRead`) can write only inside the repository. Codex runs with `--config sandbox_workspace_write.writable_roots=[]`; `--add-dir` outside the repository or under the controller's `.hermes` directory is refused with `ADD_DIR_WRITABLE_REFUSED`. In Obsidian mode the controller container (playbooks, briefs) is passed with `--read-dir`: read-only Claude receives it as `--add-dir`, Codex reads it through its sandbox, and a Claude stage with write tools is refused, so the worker process itself cannot write `GATES.md`, STATE or the journal. The pinned hashes above stop any gate under a changed `GATES.md`/`EXECUTORS.md`, and `sdd.py accept` refuses a STATE that changed outside the journal's own commit (`STATE_MODIFIED_DURING_ACTION`, whose exit is the printed `sdd.py abandon`: the open action is archived as evidence, its result is never folded in, and STATE returns to IDLE so the demand can be re-run). `sdd.py next` raises both detections itself, before printing any command, so the controller never runs a batch that can only refuse. A policy file that cannot be hashed at all (missing or unreadable) stops with `CONTROLLER_POLICY_UNREADABLE` and prints `sdd.py restore-policy --name <policy> --skill <installed-skill>` followed by `confirm-policy` (Git cannot restore it: the container is not a Git repository and a `--local-storage` controller is excluded from Git); confirming it in place is refused, because pinning the empty digest would make every gate ask for the same confirmation again.
- **Gates run repository code on the host.** A worker cannot write the container, but code it writes into the repository can: a gate such as the focused tests runs the project's test runner with the user's privileges, `cwd` = the repository and no sandbox, and that runner executes whatever the worker left there (a `conftest.py`, a test file, a build script, a config the tool loads). That code can read and write `GATES.md`, `EXECUTORS.md`, STATE and the journal in the vault like any other process of the user. This is inherent to running tests and is not sandboxed. Run gates only on a machine and account you would let run the repository's code, and in REVIEW read the diff of every test, fixture, build and tool-configuration file the worker touched before running a gate on it.
- **Project agent configuration is never loaded.** `claude -p` runs with the repository as `cwd` and skips the workspace-trust dialog, so by default it would load `.claude/settings.json`/`settings.local.json` (hooks run as the user, outside every tool restriction), `.mcp.json` servers and `.claude/skills`, all files a writing worker can create for the next stage. Every Claude call, dispatch and `--probe` alike, therefore passes `--setting-sources user --strict-mcp-config --disable-slash-commands`: only the user's own settings load, no MCP server is started (none is passed with `--mcp-config`) and skills are disabled; `preflight` returns `EXECUTOR_CLI_UNSUPPORTED` for a CLI whose help lacks any of these flags. `--bare` is not used because it also turns off OAuth/keychain login. `CLAUDE.md`/`AGENTS.md` in the repository can still be loaded as instructions (text, never executed); the controller's prompt and contract take precedence and REVIEW reads their diff. Codex `exec` has no flag that ignores project configuration (`--ignore-user-config` drops only `$CODEX_HOME/config.toml`). With codex-cli 0.160.0, a repository's `.codex/config.toml` (`notify`, `[mcp_servers]`) and `.codex/hooks.json` did not run in an untrusted repository, but the launcher cannot prove that for every version or for a repository the user marked trusted in `~/.codex/config.toml`; the launcher never passes `--dangerously-bypass-hook-trust`; never mark a repository with a running demand as trusted, and treat a `.codex/` change in a worker diff as a REVIEW finding.
- The worker inherits only `PATH`, `HOME`, `LANG`, `LC_*`, `TMPDIR`, `USER`, `LOGNAME`, `SHELL`, `TERM`, `TZ`, `XDG_*` directories, certificate and proxy variables, plus its own `ANTHROPIC_*`/`CLAUDE_*` (Claude) or `OPENAI_*`/`CODEX_*` (Codex). `TYPESAFE_*`, `JEV_*`, `HERMES_*` and every other `*_API_KEY`/`*_TOKEN` are dropped.
- On timeout, SIGTERM or SIGHUP the launcher kills the worker's process group (TERM, then KILL). A grandchild that calls `setsid` leaves that group and can survive; the CLIs are trusted not to do that.

## Before the first demand

Run `python3 .hermes/orchestration/runtime/executor_launch.py preflight --executor <claude|codex> [--model <model>] --probe` for every executor this file selects. `READY` means the CLI, its required flags, the login and the model work. `BLOCKED` names the reason and the fix.
