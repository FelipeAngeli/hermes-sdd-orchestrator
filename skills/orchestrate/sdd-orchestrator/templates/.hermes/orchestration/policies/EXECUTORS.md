# Executors

Project-owned file. It selects, per stage, which external CLI runs the worker, which model it uses, and its hard timeout. Edit the JSON block below to change executors; never edit `.hermes.md`, `LOOP_POLICY.md` or a command line for that. `runtime/executor_launch.py` is the only reader, and it is the only way to dispatch a worker.

```json
{
  "executors_version": 1,
  "stages": {
    "SPECIFY":   {"executor": "claude", "model": null, "timeout_seconds": 600, "max_turns": 40},
    "CLARIFY":   {"executor": "claude", "model": null, "timeout_seconds": 600, "max_turns": 40},
    "PLAN":      {"executor": "claude", "model": null, "timeout_seconds": 900, "max_turns": 60},
    "TASKS":     {"executor": "codex",  "model": null, "timeout_seconds": 600, "max_turns": null},
    "IMPLEMENT": {"executor": "codex",  "model": null, "timeout_seconds": 900, "max_turns": null},
    "TEST":      {"executor": "codex",  "model": null, "timeout_seconds": 600, "max_turns": null},
    "REVIEW":    {"executor": "claude", "model": null, "timeout_seconds": 600, "max_turns": 40}
  }
}
```

## Fields

- `executor`: `claude`, `codex` or `opencode`. Projects keep `claude`/`codex` unless their owner edits this file; `opencode` is optional and is never a default.
- `model`: `null` uses the CLI's configured default; otherwise a plain model name passed as `--model`.
- `timeout_seconds`: hard wall-clock limit in seconds, 1–7200. On expiry the launcher kills the whole process group and records exit code `124`.
- `max_turns`: Claude only (`--max-turns`); `null` leaves the CLI default. Codex ignores it.
- Optional `tools` (Claude `--tools`; default `Read,Grep,Glob`), `permission_mode` (Claude `--permission-mode`) and `sandbox` (Codex `read-only` or `workspace-write`; default `workspace-write` for IMPLEMENT and TEST, `read-only` otherwise).
- Optional `sandbox_network` (Codex only, default `false`): valid only for `executor: codex` with the effective `workspace-write` sandbox, otherwise `POLICY_INVALID`. When `true`, `build_argv` adds `--config sandbox_workspace_write.network_access=true` so network tests can run inside the worker sandbox.
- Optional `codex_home` (Codex only): an absolute path string outside the repository and outside the controller's `.hermes`/`Hermes` directory; it must exist at dispatch and preflight. When set, that worker receives `CODEX_HOME=<path>`, overriding any inherited `CODEX_HOME`.
- Optional `env_from` (Codex only): a list of at most 4 environment variable names matching `^[A-Z][A-Z0-9_]{0,63}$` and not starting with `TYPESAFE_`, `JEV_` or `HERMES_`, not already inherited by the worker (an exact `WORKER_ENV_NAMES` member or a `LC_`/`OPENAI_`/`CODEX_`/`ANTHROPIC_`/`CLAUDE_` prefix — for example an OpenCode key named `CODEX_*` is inherited automatically, so `env_from` is for other names) and not a loader-affecting name (`LD_*`, `DYLD_*`, `NODE_OPTIONS`, `PYTHONPATH`, `PYTHONSTARTUP`, `BASH_ENV`, `ENV`); a refused name is `POLICY_INVALID`. At dispatch each name present in the controller environment is passed to that worker only; a missing one is `EXECUTOR_ENV_MISSING` before any journal write. Names are policy data; values are never written to argv, results or the journal, and `stderr_tail` is the worker's own stderr and is not filtered.
- Optional for `opencode`: `model` is **required** and must be `provider/model` (for example `opencode-go/deepseek-v4.1-flash`); `sandbox` works as for Codex (`workspace-write` only for IMPLEMENT/TEST by default). The Codex-only keys `sandbox_network`, `codex_home` and `env_from` stay Codex-only and are `POLICY_INVALID` on an opencode stage: OpenCode always runs with sandbox network access (the seatbelt switch is all-or-nothing and the provider is remote), it has no `CODEX_HOME`, and it inherits its own `OPENCODE_*` variables minus credentials. `max_turns`, `tools` and `permission_mode` are ignored by OpenCode, whose permissions come from the fixed `OPENCODE_PERMISSION` below.
- Optional `prompt_profile`: `standard` (default) or `compact`. `compact` shortens the worker prompt: source excerpts become ±15-line windows around slice basenames, acceptance-check ids and the ticket id, controller data is rendered brief and compact, and the prompt ends with the most common rejections to re-check. Invalid values are `POLICY_INVALID`.
- Optional top-level `workspace_audit` (default `"off"`; the other accepted value is `"enforce"`, anything else is `POLICY_INVALID`). **Off by default and off for every project that does not add the field**, in which case nothing about any executor changes. With `"workspace_audit": "enforce"`, after each writing dispatch (IMPLEMENT, TEST) and for **every** executor — `claude`, `codex` and `opencode` alike — the controller compares the real repository against the snapshot it took at `prepare` (kept across the corrective retries of the same action, so a failed attempt's leftovers still count) and against the paths the result declares in `modified_paths`/`created_paths`. The snapshot covers every dirty, untracked **and ignored** file with its content hash, HEAD, the refs, the index entries with their flags, every ignore rule (`.gitignore`, `.git/info/exclude`, `core.excludesFile`), one hash of the HEAD, staged and unstaged diff, and hashes of the Git configuration (with its includes) and hooks (`core.hooksPath` and `.git/hooks`). Every `git` call is pinned to the Git directory recorded at `prepare` and to the repository as work tree, with the settings that change what Git reports (`core.worktree`, `core.bare`, `status.showUntrackedFiles`, `core.untrackedCache`, `core.fsmonitor`, external diff) overridden, so editing `.git/config` cannot redirect the audit. An undeclared change, a declared path outside the slice's `editable_paths`, a changed ignore rule, a commit, any moved ref/index or a changed Git configuration or hook stops the loop with `WORKSPACE_AUDIT_FAILED` and the result is **not** folded into STATE; the stop lists the findings and nothing is reverted automatically. It fails closed: a missing or corrupt snapshot, an unreadable result or a failing `git` call is an `AUDIT_UNVERIFIABLE` finding, and the mode recorded at `prepare` applies even if this file is edited mid-dispatch. Only the controller's own files are left out, and only when they physically live in the repository (`--local-storage`); an Obsidian container is outside the repository anyway. Besides those, and only when they are untracked and git-ignored, the audit leaves out a fixed, narrow list of files a test run rewrites every time (the names live in `runtime/detect_stack.py`, the module allowed to name toolchains; `runtime/audit_scope.py` applies them): the test runner's cache directory `.pytest_cache/` at the repository root (its whole subtree except files ending in `.py`, `.pyc`, `.pyo`, `.pth` or `.so`), the coverage data files `coverage.xml`, `.coverage` and `.coverage.*` (not ending in a code suffix) and the HTML report directory `htmlcov/` (same code-suffix rule), all at the root only, and a bytecode file directly inside a `__pycache__/` directory at any depth when its name is `<stem>.<tag>[-pytest-<version>][.opt-1|.opt-2].pyc`, `<stem>.py` exists next to that `__pycache__/`, it is a regular file and its 16-byte header is timestamp-based and records exactly that source's mtime (whole seconds) and size. A removed artifact is left out only when it is gone from disk. The filter runs when the snapshots are compared, on both sides, so an action whose baseline was stored by 15.19.0 (which still lists those files) is re-audited correctly after an upgrade. Everything else still counts: a tracked or unignored file, an undeclared source or document, a `.pyc` outside `__pycache__/`, any other file inside `__pycache__/`, an orphan or unknown-name `.pyc`, a hash-based `.pyc` (checking it would need the project's interpreter), a `.pyc` whose header does not match its source, a symlink, a `conftest.py` anywhere (also inside `.pytest_cache/`), the same names below the root, and every ignore-rule change outside `.pytest_cache/`. Linter and type-checker caches (`.mypy_cache/`, `.ruff_cache/`) are deliberately not in the list: they are gate caches, not test-run output, so a worker that runs those tools must declare or avoid them. Known limits, unchanged pending an owner decision: an embedded repository or submodule that already existed is not inspected inside (it is listed as one directory or as `-dirty`), while a newly created one is reported; a file's hash covers at most its first ~8 MiB plus its size, so a same-size edit past 8 MiB in an untracked or ignored file is not seen (`diff_sha256` is consulted only when nothing else changed); and every ignored file (`node_modules`, `.venv`, build output) is hashed, which can be slow on large repositories — `git` calls time out fail-closed at 120 s, but the hashing loop has no time budget. Finally, the bytecode rule has a residual risk: a writing worker can craft a timestamp-based `.pyc` whose header copies its source's mtime and size (both are visible to it, and it may also set the source's mtime), so the audit does not see it, and any Python process that loads the repository's `__pycache__/` (the user's own test run, an IDE, a gate process that drops the gate's `PYTHONPYCACHEPREFIX` environment, for example `python -I`) would execute that bytecode instead of the source. Gate commands themselves run with a fresh `PYTHONPYCACHEPREFIX`, so a Python that keeps that environment does not load it. The header check only rules out stale, orphan and hash-based files; it is not a content check. Projects that build with `SOURCE_DATE_EPOCH` (hash-based `.pyc`) still see those files reported.
- Optional top-level `allow_bypass_permissions` (default `false`). A stage with `permission_mode: "bypassPermissions"` is refused with `EXECUTOR_POLICY_UNSAFE` unless the owner sets `"allow_bypass_permissions": true` next to `executors_version`, accepting that the worker then runs every tool without a check.

These fields are part of the same fenced JSON block `sdd.py start` already pins by SHA-256, so they are covered by the existing `CONTROLLER_POLICY_CHANGED_DURING_DEMAND` re-verification — no extra hashing is needed.

A stage omitted from `stages` keeps the default shown above. A missing file means the same defaults. An invalid block returns `POLICY_INVALID` and nothing is dispatched.

## Trust and isolation

Whoever can edit this file chooses the program that runs, its permissions and its model, so treat it like code: only the project owner edits it, and the installer reports its SHA-256 for review. `sdd.py start` pins that SHA-256 (together with `GATES.md`) in `delivery.controller_policies`, and every `sdd.py gate` re-verifies both: a file that changed mid-demand stops the loop with `CONTROLLER_POLICY_CHANGED_DURING_DEMAND` until the user re-confirms it with `sdd.py confirm-policy --name executors --quote '<their words>'`.

**A writing worker never shares a filesystem with the controller.** A worker that can write the repository can rewrite everything the controller keeps there — this file, `GATES.md` (whose commands run on the host, outside every sandbox), `runtime/*.py`, the stage briefs, STATE and the journal — *and* every hash those would be checked against, because each anchor lives in that same writable tree. A worker that edits a file and its anchor in one step leaves nothing to detect, so detection is not the boundary here: the dispatch is refused. With the controller inside the repository (`--local-storage`), a writing stage (IMPLEMENT, TEST) stops with `CONTROLLER_WRITABLE_BY_WORKER` and is never dispatched, also when the action was already PREPARED. The criterion is the controller's physical location inside the repository (a device/inode ancestor walk), not the storage label. `migrate_to_vault.py` is not the exit: it moves STATE and the journal but keeps `runtime/*.py` and `policies/` in the repository by design. The exit is to abandon the demand (`sdd.py abandon`), reinstall the controller in Obsidian mode with `install_project.py --obsidian-vault <vault>` (its container is never a writable root for a worker), then start again; the stop prints these steps as `exit_commands`, including moving the old in-repository controller into `<vault>/<project>/.hermes-local-controller-backup/` and confirming the new container's policies. Read-only stages (SPECIFY, CLARIFY, PLAN, TASKS, REVIEW) keep running meanwhile, since a worker that cannot write cannot rewrite the controller. Obsidian storage is the only configuration that runs a writing worker at all.

The checks below stay as defence in depth — they catch the accident, a careless edit and anything that reaches these files outside a dispatch — but they are no longer what stands between a hostile writing worker and the host.

- A writing worker (Codex with `workspace-write`, or Claude with any tool other than `Read`, `Grep`, `Glob`, `LS`, `NotebookRead`) can write only inside the repository. Codex runs with `--config sandbox_workspace_write.writable_roots=[]`; `--add-dir` outside the repository or under the controller's `.hermes` directory is refused with `ADD_DIR_WRITABLE_REFUSED`. In Obsidian mode the controller container (playbooks, briefs) is passed with `--read-dir`: read-only Claude receives it as `--add-dir`, Codex reads it through its sandbox, and a Claude stage with write tools is refused, so the worker process itself cannot write `GATES.md`, STATE or the journal. The pinned hashes above stop any gate under a changed `GATES.md`/`EXECUTORS.md`, and `sdd.py accept` refuses a STATE that changed outside the journal's own commit (`STATE_MODIFIED_DURING_ACTION`, whose exit is the printed `sdd.py abandon`: the open action is archived as evidence, its result is never folded in, and STATE returns to IDLE so the demand can be re-run). `sdd.py next` raises both detections itself, before printing any command, so the controller never runs a batch that can only refuse. A policy file that cannot be hashed at all (missing or unreadable) stops with `CONTROLLER_POLICY_UNREADABLE` and prints `sdd.py restore-policy --name <policy> --skill <installed-skill>` followed by `confirm-policy` (Git cannot restore it: the container is not a Git repository and a `--local-storage` controller is excluded from Git); confirming it in place is refused, because pinning the empty digest would make every gate ask for the same confirmation again.
- **Gates run repository code on the host.** A worker cannot write the container, but code it writes into the repository can: a gate such as the focused tests runs the project's test runner with the user's privileges, `cwd` = the repository and no sandbox, and that runner executes whatever the worker left there (a `conftest.py`, a test file, a build script, a config the tool loads). That code can read and write `GATES.md`, `EXECUTORS.md`, STATE and the journal in the vault like any other process of the user. This is inherent to running tests and is not sandboxed. Run gates only on a machine and account you would let run the repository's code, and in REVIEW read the diff of every test, fixture, build and tool-configuration file the worker touched before running a gate on it.
- **Project agent configuration is never loaded.** `claude -p` runs with the repository as `cwd` and skips the workspace-trust dialog, so by default it would load `.claude/settings.json`/`settings.local.json` (hooks run as the user, outside every tool restriction), `.mcp.json` servers and `.claude/skills`, all files a writing worker can create for the next stage. Every Claude call, dispatch and `--probe` alike, therefore passes `--setting-sources user --strict-mcp-config --disable-slash-commands`: only the user's own settings load, no MCP server is started (none is passed with `--mcp-config`) and skills are disabled; `preflight` returns `EXECUTOR_CLI_UNSUPPORTED` for a CLI whose help lacks any of these flags. `--bare` is not used because it also turns off OAuth/keychain login. `CLAUDE.md`/`AGENTS.md` in the repository can still be loaded as instructions (text, never executed); the controller's prompt and contract take precedence and REVIEW reads their diff. Codex `exec` has no flag that ignores project configuration (`--ignore-user-config` drops only `$CODEX_HOME/config.toml`). With codex-cli 0.160.0, a repository's `.codex/config.toml` (`notify`, `[mcp_servers]`) and `.codex/hooks.json` did not run in an untrusted repository, but the launcher cannot prove that for every version or for a repository the user marked trusted in `~/.codex/config.toml`; the launcher never passes `--dangerously-bypass-hook-trust`; never mark a repository with a running demand as trusted, and treat a `.codex/` change in a worker diff as a REVIEW finding.
- The worker inherits only `PATH`, `HOME`, `LANG`, `LC_*`, `TMPDIR`, `USER`, `LOGNAME`, `SHELL`, `TERM`, `TZ`, `XDG_*` directories, certificate and proxy variables, plus its own `ANTHROPIC_*`/`CLAUDE_*` (Claude) or `OPENAI_*`/`CODEX_*` (Codex), plus any `env_from` names the stage explicitly allowlists (and the Codex `codex_home` override). `TYPESAFE_*`, `JEV_*`, `HERMES_*` and every other `*_API_KEY`/`*_TOKEN` are dropped.
- On timeout, SIGTERM or SIGHUP the launcher kills the worker's process group (TERM, then KILL). A grandchild that calls `setsid` leaves that group and can survive; the CLIs are trusted not to do that.

## OpenCode worker (optional)

`opencode` is supported as an optional executor; no stage uses it unless this file says so. The launcher pins **opencode 1.18.34** exactly: any other version is `BLOCKED` with `EXECUTOR_CLI_UNSUPPORTED`, because the hermetic variables and permission rules below were verified only on that version. Example (the other stages stay on `claude`/`codex`):

```json
{
  "executors_version": 1,
  "stages": {
    "IMPLEMENT": {"executor": "opencode", "model": "opencode-go/deepseek-v4.1-flash", "timeout_seconds": 900},
    "TEST":      {"executor": "opencode", "model": "opencode-go/deepseek-v4.1-flash", "timeout_seconds": 600}
  }
}
```

**Never bare.** Every OpenCode call is `codex sandbox` (macOS seatbelt; it makes no model call) around `opencode run --format json --pure --auto --dir <repository> -m <model> -f <transport schema>`, so the codex CLI with its `sandbox -c/--config` subcommand is required too; `preflight` is `BLOCKED` with `EXECUTOR_UNAVAILABLE` without it.

**Hermetic configuration.** `--auto` alone is never trusted. The worker environment sets `OPENCODE_PURE`, `OPENCODE_DISABLE_PROJECT_CONFIG`, `OPENCODE_DISABLE_EXTERNAL_SKILLS`, `OPENCODE_DISABLE_CLAUDE_CODE`, `OPENCODE_DISABLE_CLAUDE_CODE_PROMPT`, `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS`, `OPENCODE_DISABLE_DEFAULT_PLUGINS`, `OPENCODE_DISABLE_AUTOUPDATE`, `OPENCODE_DISABLE_SHARE` and `OPENCODE_DISABLE_LSP_DOWNLOAD`, so a repository's `opencode.json`/`.opencode/plugins`, the user's own plugins and every external skill directory stay unloaded. `OPENCODE_PERMISSION` then denies `webfetch`, `websearch`, `codesearch` and `task`, denies every `external_directory`, denies `edit` outside the workspace (`../*`) and in `.git`, and denies the `read` tool on OpenCode's `auth.json`/`opencode.db*` and any `bash` command naming them (defence in depth: the seatbelt must let OpenCode read its own data directory, so the stored stream also drops every tool part). The rules are always `deny`, never `ask`: an `ask` in a non-interactive run is not a boundary. The only exception the owner approved is that each `--read-dir` path the controller passes (the Obsidian container with the brief and playbooks) gets an `external_directory` **allow** plus an `edit` **deny**, so the worker reads it and cannot write it. A read-only stage denies `edit` everywhere. The launcher prints the SHA-256 of that effective configuration (`opencode_config_sha256`) with the executor version and model in every `build`/`run` result.

**Isolation.** Writable roots are the workspace plus OpenCode's own data directory (`$XDG_DATA_HOME/opencode`, default `~/.local/share/opencode`), with `exclude_slash_tmp` and `exclude_tmpdir_env_var`. For a writing stage the workspace is the repository; for a read-only stage it is a per-dispatch directory inside that data directory, with `--dir <repository>` so the worker still reads the repository but cannot write it (Codex's read-only sandbox mode cannot add a writable root, so this layout is the minimal safe equivalent). `.git`, `/tmp`, `$TMPDIR`, `~/.config/opencode`, the controller container and the rest of the vault are refused by the seatbelt itself, which is verified with the real binaries in `tests/test_opencode_isolation.py`. The data directory holds the logged-in OpenCode account and is used **in place**: no credential is read, copied, exported or printed, and nothing is created there besides OpenCode's own state and the per-dispatch directory `sdd-runtime/<dispatch>/` (config, cache, state, tmp, work), which is deleted after the dispatch. Sandbox network access is on for every OpenCode stage because the provider is remote and the seatbelt switch is all-or-nothing: it cannot be narrowed to one host.

**Output.** OpenCode's JSONL stream is read fail-closed (`runtime/opencode_transport.py`): exactly one final text in the last step, which must end with `reason: "stop"`, validated by the same transport schema and `validate_protocol.py` path as the other executors. The outcome classes are `OK`, `INVALID_OUTPUT`, `PARTIAL`, `TIMEOUT`, `CRASH` and `ERROR_EVENT`, mapped onto the existing statuses `ARTIFACT_READY`, `OUTPUT_INVALID`, `EXECUTOR_NO_OUTPUT`, `EXECUTOR_TIMEOUT` and `EXECUTOR_FAILED`. The raw stream is kept next to the final file as `<final>.raw-stream.jsonl` with only its `step_start`, `text`, `step_finish` and `error` events (never a tool's input, output or metadata), after `runtime/redaction.py redact()`; `stderr_tail` and the probe's `probe_stderr_tail` are redacted for this executor.

**Environment.** OpenCode inherits the base variables plus `OPENCODE_*`, except `OPENCODE_API_KEY`, `OPENCODE_CONSOLE_TOKEN`, `OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR`, `OPENCODE_CONFIG_CONTENT`, `OPENCODE_PERMISSION`, `OPENCODE_SERVER_PASSWORD`, `OPENCODE_SERVER_USERNAME` and any `OPENCODE_*` name ending in `_KEY`, `_TOKEN`, `_SECRET` or `_PASSWORD`, which are dropped so an inherited credential or configuration redirection cannot reach the worker. `TYPESAFE_*`, `JEV_*`, `HERMES_*` and other `*_API_KEY`/`*_TOKEN` are dropped as for every executor. `--add-dir` is refused for OpenCode (`ADD_DIR_WRITABLE_REFUSED`): its writable roots are fixed.

## Before the first demand

Run `python3 .hermes/orchestration/runtime/executor_launch.py preflight --executor <claude|codex|opencode> [--model <model>] [--stage <STAGE>] [--probe-sandbox] --probe` for every executor this file selects. `READY` means the CLI, its required flags, the login and the model work. `BLOCKED` names the reason and the fix. With `--stage <STAGE>` the stage's fields (including `codex_home`, `env_from` and `sandbox_network`) are loaded from this file, the model probe runs with that stage's worker environment, and `--probe-sandbox` additionally runs the Codex `workspace-write` sandbox probes (TCP listen, Unix-socket listen, `docker info`) without a model call and reports `sandbox_probe` plus the advisory warnings `SANDBOX_NETWORK_ENABLED` (the stage sets `sandbox_network`) and `SANDBOX_NETWORK_REQUIRED` (a probe was blocked and the stage does not set `sandbox_network`). `--probe-sandbox` requires `--stage`. Each probe is `OK`, `BLOCKED`, `SKIPPED`, `ERROR` or `UNSUPPORTED`: before probing, `codex sandbox --help` must list `-c`/`--config` (otherwise every probe is `UNSUPPORTED` and no `SANDBOX_NETWORK_REQUIRED` warning is added); `docker info` first runs once unsandboxed as a baseline with the same short timeout, so a missing Docker daemon is `SKIPPED` and only a baseline that succeeds with a blocked sandboxed `docker info` is `BLOCKED`.
