# Validation gates (opt-in, observation mode)

[Docs index](../README.md) · Related: [Loop engine](loop-engine.md), [Gates and stack detection](gates-and-stack-detection.md), [Contracts and schemas](contracts-and-schemas.md)

**Files:** `runtime/gate_registry.py`, `runtime/gate_validator.py`, `runtime/gate_workspace.py`, `runtime/gate_stages.py`, `runtime/gate_reviewer.py`, `runtime/gate_evidence.py`, `runtime/gate_corrections.py`, `runtime/gate_engine.py`, `runtime/gate_cli.py`, `schemas/GATE_DECISION_SCHEMA.json`.

Formal, auditable validation criteria for every SDD stage, inspired by the gates and goal evaluators of CompozyOS. **Nothing in the controller calls them**: `sdd.py`, the drivers and `policies/GATES.md` behave as before. The default mode is `OBSERVE`: every evaluation is recorded and nothing is blocked. They run only through `gate_cli.py evaluate`, `gate_engine.GateEngine` in a host program, or `gate_engine.gated_handler` around a [loop engine](loop-engine.md) handler.

## Components

| Component | Module | Role |
| --- | --- | --- |
| GateRegistry | `gate_registry` | Catalogue: one gate per stage (`gate_id` `sdd.<stage>`), each with criteria `{id, description, evaluator, on_fail}`. `evaluator` is `DETERMINISTIC` or `AGENT`; `GateRegistry.digest()` is part of every decision key, so a changed criterion never reuses an old decision. |
| DeterministicValidator | `gate_validator`, `gate_stages`, `gate_workspace` | Checks the artifact against its JSON Schema (artifacts over `gate_stages.MAX_ARTIFACT_BYTES`, 2 MiB, fail it) and runs the stage's checks against the real workspace and real commands. |
| AgentReviewer | `gate_reviewer` | Asks independent reviewers about the `AGENT` criteria with minimal context. |
| EvidenceCollector | `gate_evidence.EvidenceCollector` | Content-addressed, versioned, redacted evidence records. |
| GateDecision | `gate_engine`, `gate_evidence.DecisionLog`, `GATE_DECISION_SCHEMA.json` | Combines the results into one structured decision in an append-only, hash-chained log. |

## Gates per stage

| Stage (`GATE_STAGES`) | Criteria (DETERMINISTIC unless marked AGENT) |
| --- | --- |
| SPECIFY | `SCHEMA_VALID`, `SCOPE_STATED` (non-empty summary), `ACCEPTANCE_CRITERIA_DEFINED` (a check with criterion and verification method), `NO_BLOCKERS` |
| CLARIFY | `SCHEMA_VALID`, `NO_OPEN_MATERIAL_QUESTIONS` (BLOCKED), `MATERIAL_ASSUMPTIONS_VALIDATED` (BLOCKED), `NO_BLOCKERS` |
| PLAN | `SCHEMA_VALID`, `IMPACT_FILES_EXIST` (each file exists in the repository), `DECISIONS_RECORDED`, `INDEPENDENT_REVIEWER`, `FEASIBILITY` (AGENT: dependencies and risks), `NO_BLOCKERS` |
| TASKS | `SCHEMA_VALID`, `TASKS_DEFINED`, `CHECKS_TRACED_TO_SLICES`, `CHECKS_HAVE_VERIFIERS` (each AGENT check names a backticked verifier), `NO_BLOCKERS` |
| IMPLEMENT | `SCHEMA_VALID`, `CLAIMS_MATCH_WORKSPACE` (reported files = the files that differ on disk from `context.base_commit`, or from HEAD without a base; an invalid base or a repository with submodules is BLOCKED; an unreadable workspace, a tampered object store or a scan over `MAX_SCAN_BYTES` is INCONCLUSIVE), `WITHIN_EDITABLE_PATHS`, `STATIC_ANALYSIS` (the configured Analyze command), `NO_BLOCKERS` |
| TEST | `SCHEMA_VALID`, `TESTS_CONFIGURED` (BLOCKED), `TESTS_EXIST` (files the test command names exist), `TESTS_PASS` (the gate runs Focused tests itself), `EVIDENCE_REPRODUCED` (claimed passing commands are re-run; a claim whose argv equals a configured gate command is re-run first as that configured command, so neither cheap claims nor a disallowed spelling can hide a false claim about it; spellings are deduplicated by argv; at most `MAX_REPRODUCED` = 10, and claims over the cap make it INCONCLUSIVE), `CHECKS_COVERED` (each AGENT check has a controller-bound verifier or waiver), `EXPECTED_CHECKS_STATED` (BLOCKED unless the controller gives `expected_check_ids`, `check_commands` or `waivers`), `ACCEPTANCE:<id>` per check, `NO_BLOCKERS` |
| REVIEW | `SCHEMA_VALID`, `REVIEW_APPROVED` (APPROVED and every finding's severity, trimmed and case-folded by `gate_stages.severity_key`, in `gate_stages.NON_BLOCKING_SEVERITIES`: LOW, INFO, NOTE, MINOR, NIT, NON_BLOCKING, NONE, NO_FINDINGS), `RECORDED_GATES_PASS` and `BASELINE_AND_OWNERSHIP` (consistency of what the review reports), `TESTS_PASS`, `STATIC_ANALYSIS` and `FORMAT` (the gate re-runs Focused tests, Analyze and, when configured, Format itself), `EXPECTED_CHECKS_STATED`, `ACCEPTANCE:<id>` per check, `INDEPENDENT_REVIEWER`, `FUNCTIONAL_ADHERENCE`, `SECURITY`, `INTEGRATION` (all three AGENT) |

`ACCEPTANCE:<id>` passes only when the check's bound verifier (`context.check_commands`) is a configured gate command or a command `acceptance_verifiers.allowed_check_command` accepts, and the gate runs it and gets exit 0, or when the controller recorded a waiver for it (`context.waivers`). A waiver written only in the artifact is BLOCKED; a HUMAN check is BLOCKED until a human decides; a check with only prose evidence fails: a textual answer is not proof. The expected checks are the union of the bound, waived and `context.expected_check_ids` ids (plus `acceptance.expected_check_ids` at REVIEW): an expected check the artifact leaves out fails.

The checks are language-neutral: commands come from the Focused tests and Analyze rows of `policies/GATES.md` (`gate_cli.gate_commands`) or from the host's `commands` mapping.

## Controller-owned context

`context` keys (`gate_engine.CONTEXT_KEYS`): `check_commands`, `editable_paths`, `implementer`, `waivers`, `expected_check_ids`, `base_commit` (the full object id of the commit the slice started from; it must be an ancestor of HEAD, so a ref name or an unrelated commit is refused). They must come from the controller's own state (for example the verifier binding, the human-decision journal and the recorded base), never from a worker artifact; other keys are dropped. All of them are part of the decision key. `gate_cli evaluate` without `--context` gives none, so TEST and REVIEW are BLOCKED on `EXPECTED_CHECKS_STATED`. The evidence store must be outside the repository (`GATE_STORE_INSIDE_REPO`).

## Rules

- **Evidence, not text.** Every criterion stores what it looked at (`EvidenceCollector.put`); a worker's claim is checked against the workspace or re-run. A PASS always has evidence references beyond the artifact itself, or it becomes INCONCLUSIVE (`EVIDENCE_PRESENT`).
- **Tests are not replaced by judgement.** Test criteria are DETERMINISTIC, and AGENT criteria are asked only when no deterministic criterion FAILed, so a reviewer can never overrule a failing test.
- **Inconclusive is never success.** A timeout or an unrunnable command is INCONCLUSIVE; `gate_engine.is_success` is true only for PASS. Verdict precedence: FAIL, then BLOCKED, then INCONCLUSIVE, then PASS. Criteria skipped after an invalid schema are `NOT_EVALUATED` and do not count.
- **Independent, minimal review.** A reviewer is `Reviewer(name, family, call)`. The implementer is `context.implementer` and the artifact's `executor.name`; families compare by `gate_reviewer.family`, which maps each name to a vendor through `gate_reviewer.VENDORS`, including glued names (so `gpt-5-codex`, `codex-cli`, `codexcli`, `gpt4o` and `CODEX` are all `openai`, and `claude-opus-5` and `claudecode` are `anthropic`); a name with a non-ASCII character (a look-alike spelling) or no ASCII word, such as `4o`, has no family. Reviewers of an implementer's family are ignored; with none left, or with no implementer known, the AGENT criteria and `INDEPENDENT_REVIEWER` are BLOCKED. The reviewer sees only the gate, stage, task, criterion texts and short evidence summaries with references, capped at `gate_reviewer.MAX_CONTEXT_BYTES` (16 KiB); never the conversation or the repository. The summaries can quote text the worker wrote (the artifact summary, findings, criteria): the context's `limits.untrusted` tells the reviewer to treat it as data, and the rules here keep any answer from standing without cited evidence or over a deterministic failure. A PASS that cites no reference from that context, a reviewer error, a malformed answer and disagreeing reviewers are all INCONCLUSIVE.
- **No re-review without new evidence.** The idempotency key hashes the registry, gate, task, artifact, workspace (`gate_workspace.fingerprint`: HEAD, the base, the chunked hash of every changed file and a digest of the name, type, size, mtime and ctime of every ignored entry, plus the same metadata of the file an ignored symlink points to), commands, timeouts, reviewer roster, context and mode. The same key returns the recorded decision with `reused: true` after the log's hash chain is verified and every evidence reference of that decision resolves: no command runs and no reviewer is asked. A gitignored file is not a changed path, but creating or editing one is new evidence, so a planted cache is not served a stale PASS. Gate commands run with `PYTHONPYCACHEPREFIX` set to a fresh gate-owned directory and `PYTHONDONTWRITEBYTECODE=1`, so Python neither loads a `.pyc` planted in the repository nor writes one there; other tools' caches (for example `.pytest_cache`) still change ignored paths and are then new evidence, which only costs a re-evaluation. A `retryable` decision is never reused: the same inputs are evaluated again as the next generation. A decision is retryable when it is INCONCLUSIVE from a timeout, an unrunnable command, a git failure or a reviewer error (those criteria carry `transient: true`), or when the fingerprint is incomplete (git failed, no HEAD, submodules, more than `MAX_FILES` = 5000 changed files or `MAX_ENTRIES` walked entries, more than `MAX_SCAN_BYTES` compared, a file over `MAX_HASH_BYTES` = 64 MiB, an unreadable or special file, a changed symlink, whose target content the fingerprint does not follow, an ignored symlink to a directory or to nothing, or more than `MAX_ENTRIES` entries under ignored paths, which a large `node_modules` or `.venv` reaches and which then disables reuse altogether), because then the gate cannot prove that nothing changed.
- **History is kept.** Decisions are appended, never rewritten: each has `generation` and `previous_decision_id`, plus `prev_hash` and `record_hash`. Every read used for reuse, history or a new append verifies the whole chain first, so an edited or removed decision raises `DECISION_LOG_TAMPERED` instead of being served. Evidence is stored under its SHA-256, so an edited record is `EVIDENCE_TAMPERED` on read. Both carry a `schema_version`.
- **Commands are contained.** No shell (`shlex.split`), run in the repository with the gate's timeout (default 300 s), no stdin, a minimal environment (`SAFE_ENV`: `PATH`, `HOME`, `LANG`, `LC_ALL`, `TMPDIR`, `SYSTEMROOT`, `PYTHONPATH`, `VIRTUAL_ENV`) and output written to temporary files, of which only the end window is read back, redacted and then cut to 4 000 characters. Every string written to evidence or the decision log goes through `redaction.redact`.
- **Content is compared by the gate, not by git.** Git would apply the worker's attributes (`ident`, `eol`, filter drivers, whose names `-c` cannot always even address), its stat cache and its index flags, and any of them can hide an edit or run a program. Git also does not re-hash an object when it reads one, so a worker that rewrites a tree object in `.git/objects` could make an edited file look like the base. So `gate_workspace.scan` reads the reference commit (`context.base_commit`, or HEAD without one) and every tree under it with `git cat-file --batch`, re-hashes each object itself and parses the trees itself; a mismatch makes the scope checks INCONCLUSIVE. It then compares every tracked path on disk: the git blob id of the raw bytes (or of a symlink's target), the executable bit and the file type, and a tracked directory that is now a symlink, a file or missing reports itself and everything under it. It walks the working tree itself (skipping only the top-level `.git`, so a nested repository is walked like any directory), and an untracked path counts unless a `.gitignore` that is unchanged from the reference tree ignores it (`git check-ignore --no-index` reports which rule decided, negations included), so a rule the worker wrote or edited, `.git/info/exclude` and `core.excludesFile` hide nothing; a rule that ignores a directory holding tracked files hides nothing under that directory. The only git calls are `rev-parse`, `merge-base`, `cat-file --batch` and `check-ignore`; none reads the index or file contents, so filters, attributes, hooks and fsmonitor never run. Git runs with a minimal environment (`GIT_SAFE_ENV`, no system or global config, no replace refs or grafts, no lazy fetch from a promisor remote (`GIT_NO_LAZY_FETCH`, which would otherwise run the repository's `core.sshCommand`), `HOME` set to the null device, no stdin), `GIT_DIR` and `GIT_WORK_TREE` pinned to the repository so `core.worktree` cannot redirect it, and the settings that change ignore matching pinned (`FIXED_OVERRIDES`). A commit since the base, a rename (both paths) and a staged new file are all reported. Submodules are not supported: a reference tree with one makes the scan BLOCKED.

## GateDecision

`GATE_DECISION_SCHEMA.json` (v1, closed): `gate_id`, `task_id`, `verdict` (`PASS` | `FAIL` | `BLOCKED` | `INCONCLUSIVE`), `evidence_refs` (`sha256:<hex>`), `failed_criteria` (`{id, status, refs, detail}`), `suggested_actions`, `evaluator` (`gate_engine/deterministic`, plus `+agent:<names>` when reviewers were asked), `timestamp` (UTC ISO 8601), and also `decision_id`, `stage`, `criteria`, `generation`, `previous_decision_id`, `idempotency_key`, `registry_sha256`, `artifact_sha256`, `mode`, `blocking`, `retryable`, `corrective_task`, `prev_hash`, `record_hash`. The value `evaluate` returns adds `reused`, which the schema allows and the log never stores. The schema requires evidence and no failed criteria for every PASS.

## Correction control

A FAIL produces a `corrective_task` (`gate_corrections`): the failure is classified (`TEST_FAILURE`, `MISSING_TEST`, `FALSE_EVIDENCE`, `ACCEPTANCE_UNMET`, `STATIC_ANALYSIS`, `SCOPE_VIOLATION`, `REVIEW_FINDINGS`, `GATE_FAILURE`, `CONTRACT_INVALID`, `ARTIFACT_INCOMPLETE`), the smallest unit is named (one acceptance check, the failing command, the files outside scope, or the stage), and the task carries the stage to re-run (IMPLEMENT for failures found at IMPLEMENT, TEST or REVIEW; the stage itself otherwise), the failed criteria, one hypothesis, the evidence and a scope limit. BLOCKED and INCONCLUSIVE never produce a task: they need a human or new evidence, not a code change.

`gate_engine.gated_handler(gates, handler, task_id=..., context=...)` wraps a loop-engine stage handler and evaluates `output.artifact`. In `OBSERVE` it only attaches `output.gate`. In `ENFORCE` a FAIL becomes a FUNCTIONAL failure carrying `failed_checks`, `hypothesis` and `evidence`, which the loop engine's bounded correction turns into a corrective IMPLEMENT run; the next evaluation sees the new workspace, so it is a new generation. BLOCKED becomes a FUNCTIONAL failure without a correction and INCONCLUSIVE an UNKNOWN failure; the loop engine escalates both to a human.

## Modes

`MODES`: `OBSERVE` (default) records decisions with `blocking: false`; `ENFORCE` sets `blocking: true` on any verdict other than PASS. Promote to `ENFORCE` only after observing decisions on real demands.

## Quality report

The suites `test_gates_acceptance.py`, `test_gates_rules.py`, `test_gates_units.py`, `test_gates_review.py`, `test_gates_hardening.py`, `test_gates_round3.py`, `test_gates_round4.py`, `test_gates_round5.py` and `test_gates_round6.py` (125 tests) cover the eight required scenarios — correct code, failing test, missing test, false evidence, contradictory reviewers, inconclusive result, unmet acceptance criterion, a failure fixed in a new generation — plus the business rules, every stage gate, the loop-engine integration in both modes, the decision schema, redaction, the minimal environment, no shell, and the review regressions: forged waivers, dropped checks, a REVIEW that re-runs the tests, an unknown or renamed implementer, tampered reuse, hardened git, renames and the re-run cap, and the second review round: base-commit diffs, local excludes, index flags, filter drivers, incomplete fingerprints, a workspace outside git, the store inside the repository, Format at REVIEW, severity spellings, the claim order and dedupe, the expected-check set, vendor families and glued tokens; and the third: index flags against reuse, `core.worktree`, worktree-config filters, replace refs, stat-cache settings, worker-written ignore rules, invalid bases, unreadable and special files, hooks and external diff drivers, claim spellings of a configured command, REVIEW without an expected set, padded severities and glued or look-alike executor names; and the fourth: a filter named with `=`, `ident` and `eol` attributes in the tree, in `.git/info/attributes` and in `core.attributesFile`, a refreshed stat cache, index flags with a base, a staged file and a committed rename, an embedded repository, a base negation rule, submodules, and no git call reading content; and the fifth: a rewritten tree object, a promisor lazy fetch, a changed symlink, a tracked directory replaced by a symlink, an ignored directory holding tracked files, a planted bytecode cache, the gate's own caches and running out of scan budget; and the sixth: an ignored symlink into `.git`, an ignored symlink to a directory, too many ignored entries, a cache the gate's command plants, and a planted `.pyc` a fresh run must not load. Two independent mutation runs removed rules one at a time: the first (26 rules) and the reviewers' second run (38 rules) left 3 and 12 survivors, each now covered by a test; a third run of 29 rules (those 12 and every rule added since) left 4, which were then covered (3 by sharper tests, 1 by removing a redundant duplicate check) and re-run as killed. The reviewers' third run (67 rules) left 12; the follow-up runs are reported in the changelog entry of each release. Mutation runs show the tests notice a removed rule; they do not prove the rule set complete.

Limits, stated plainly:

- A reviewer's honesty is not verified: the rules only ensure it is independent by family, sees minimal context and cites evidence that exists.
- `EVIDENCE_REPRODUCED` re-runs only claimed commands the gate may run (configured or allowlisted); other claims are listed as not reproducible, not as PASS.
- `TESTS_EXIST` recognises file-like arguments of the test command; a test selected only by name inside a runner (for example a `-k` expression) is not checked.
- Evidence records a workspace fingerprint (HEAD, changed-file hashes and the metadata of ignored entries); it does not snapshot file contents. Files a `.gitignore` in the reference tree excludes are outside the change list and the editable-path check: a rule that ignores files by pattern (`*.py`, `vendor/**/*.py`) hides new files that match it, even beside tracked ones. Only a rule that ignores a directory holding tracked files hides nothing under it.
- Git still reads the repository's own `.git` objects and refs, and without `base_commit` a worker can hide an edit by committing it (HEAD is then the reference). Keep `.git` out of the worker's reach and pass `base_commit`.
- A sparse checkout's excluded paths are missing on disk, so they are reported as changed (fail closed).
- Every evaluation reads every tracked file, bounded by `MAX_SCAN_BYTES`; above it the scope checks are INCONCLUSIVE. It also stats every entry under ignored paths; above `MAX_ENTRIES` the fingerprint is incomplete and no decision is reused.
- A fresh evaluation runs whatever the worker left on disk. With bytecode redirected, a planted `.pyc` is not loaded, but other tools may still read caches the worker wrote.
- Gate commands run the worker's code as the gate's own user: they can write anything that user can, including the store. The store-outside-repository rule and the hash chain detect accidents and naive edits, not a same-user attacker that rebuilds the chain; run the gates from a separate user or sandbox before trusting them against an adversarial worker.
- `context` is trusted: the gate cannot tell whether a caller passed controller state or worker output.

## Rollback

Nothing in the controller imports these modules. Revert the change to remove them; delete a store directory to discard its decisions and evidence.
