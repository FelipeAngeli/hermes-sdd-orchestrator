# Contracts and schemas

[Docs index](../README.md) · Related: [Stage agents](stage-agents.md), [Sub-agents](sub-agents.md), [Action journal](action-journal.md), [Gates](gates-and-stack-detection.md)

**Files:** `contracts/EXECUTOR_CONTRACT.md`, `contracts/REVIEW_CONTRACT.md`, `schemas/EXECUTOR_RESULT_SCHEMA.json`, `schemas/REVIEW_RESULT_SCHEMA.json`, `schemas/DECISION_REQUEST_SCHEMA.json`, `schemas/DECISION_RECEIPT_SCHEMA.json`, `schemas/AGENT_REGISTRY_SCHEMA.json`, `schemas/DELEGATION_CONTRACT_SCHEMA.json`, `runtime/decision_orchestration.py`, `runtime/validate_protocol.py`, `runtime/executor_launch.py`, `runtime/executor_dispatch.py`, `runtime/dispatch_audit.py`, `runtime/audit_scope.py`, `runtime/opencode_executor.py`, `runtime/opencode_transport.py`, `runtime/executor_transport.py`, `runtime/executor_sandbox.py`, `policies/EXECUTORS.md`.

Every worker ends with **one JSON document**, written to a unique final-message file. Markdown, YAML, transcripts and JSONL events are never accepted as a substitute. Both envelopes use `schema_version: 3` and reject unknown properties. Each [stage agent](stage-agents.md) and [sub-agent](sub-agents.md) declares which schema applies in its `result_schema` frontmatter.

The additive agent-manager schemas are version 1: `AGENT_REGISTRY_SCHEMA.json` closes the deterministic read-only registry, and `DELEGATION_CONTRACT_SCHEMA.json` closes a proposed delegation request. Their current behavior is documented in [Agent manager](agent-manager.md); neither changes the existing executor or review envelopes. The experimental loop engine adds `LOOP_DEFINITION_SCHEMA.json` and `LOOP_EXECUTION_SCHEMA.json` (v1), documented in [Loop engine](loop-engine.md). The opt-in validation gates add `GATE_DECISION_SCHEMA.json` (v1), documented in [Validation gates](validation-gates.md). The opt-in security policy engine adds `SECURITY_POLICY_SCHEMA.json` (v1) for `policies/SECURITY_POLICY.json`, documented in [Security policy engine](policy-engine.md).

## Typed Jev decisions

`runtime/decision_orchestration.py` is a subordinate, side-effect-free decision primitive. `DECISION_REQUEST_SCHEMA.json` bounds one decision to a ticket, stage and STATE SHA-256; a closed candidate map with printable names of at most 64 characters; a deterministic baseline; compact scalar signals; evidence IDs; and one mode: `OFF`, `SHADOW`, `ACTIVE` or `FALLBACK`. Supported kinds cover task, skill, agent, model, context, risk, completion and escalation decisions. The module converts the whole control binding (ID, kind, mode, stage/STATE and baseline), not only semantic evidence, to one `semantic_governor` choice request so its cache fingerprint authenticates the operating mode used by the stage gate.

`DECISION_RECEIPT_SCHEMA.json` records baseline, Jev recommendation, confidence/disposition/provenance/fingerprint, effective mode, agreement, whether a recommendation was applied, review status and observed request bytes, elapsed milliseconds, calls, token usage and provider billing. State that matches the shared redactor is rejected before evaluation. `OFF` never calls Jev; `SHADOW` never changes the baseline; `ACTIVE` can apply only a decided closed candidate; `FALLBACK` preserves the baseline on `REVIEW`. An explicit user lock always wins, and `COMPLETION_ASSESSMENT` cannot select `COMPLETE` while deterministic readiness is false.

The first controller integration is deliberately narrower than the generic contract: `sdd.py govern` runs `AGENT_SELECTION` in `SHADOW` before PLAN and IMPLEMENT. It compares `STAGE_AGENT` with `DATA_FLOW_TRACER`, stores the receipt in `delivery.semantic_decisions`, and exposes the typed request plus cached governor fingerprint/mode to the stage manifest. The checker recomputes that request's provider-specific fingerprint before allowing a `SHADOW` `REVIEW` to preserve the baseline; a caller-written `mode: SHADOW` without the bound request cannot bypass human review. No recommendation is executed in this rollout.

## Executor result

Used by `SPECIFY`, `CLARIFY`, `PLAN`, `TASKS`, `IMPLEMENT` and `TEST`, and by the sub-agents that declare `EXECUTOR_RESULT_SCHEMA.json`. The root is `executor_result`, with these required fields: `schema_version`, `stage` (`value`, `status`), `executor` (`name`: `CODEX`, `CLAUDE` or `OPENCODE`; `invocation_type`: `EXTERNAL_CLI`), `consulted_paths`, `modified_paths`, `created_paths` (objects `{path}`), `validated_symbols`, `commands`, `blockers`, `context_assessment`, `acceptance_checks`, `stage_payload` (`summary`, `tasks`, `impact_files`, `decisions`), `tdd_slices` and `next_step` (never `DONE`).

**Context.** `context_assessment` separates evidence-backed facts from assumptions and unresolved questions. SPECIFY may succeed with unresolved material context only by routing directly to CLARIFY. From CLARIFY onward, a successful result cannot retain an unvalidated material assumption or a material unresolved question; the worker must obtain evidence or return a blocker instead of guessing.

**Acceptance evidence.** Each `acceptance_checks` item has a stable unique ID, criterion, verification method, verifier, nullable slice assignment, status and evidence. The controller-owned mapping includes ID, criterion, verification method, verifier and a non-whitespace slice assignment for every check; workers cannot downgrade a HUMAN check to AGENT, replace its method or erase its slice. SPECIFY through PLAN always keep checks `PLANNED` with null evidence; TASKS success requires a non-empty set with every check assigned to a slice. For IMPLEMENT, the controller supplies exactly one current slice ID and disjoint completed-slice IDs; the completed set is mandatory even when explicitly empty, so omission cannot downgrade prior checks to future checks. The payload's TDD slice must match the controller-selected current ID exactly. Current/completed checks pass while future checks remain planned. TEST success requires every check at `PASS` or `WAIVED`. Every REVIEW status must match the same mapping. Context and acceptance text cannot be whitespace-only.

**`WAIVED`.** Every check carries `waiver`: `null`, or — exactly when `status` is `WAIVED` — `{by, reason, quote, recorded_at}` (the approver from PROJECT_SETUP `approvers`, default the requester; why; the literal quote of the decision; an ISO-8601 timestamp with offset), plus non-whitespace evidence. Wherever `PASS` is required (current/completed IMPLEMENT slices, TEST success, a read-only role's carried-forward checks, REVIEW `APPROVED`), `WAIVED` satisfies it (`SATISFIED_STATUSES`). A `HUMAN` check may carry its own waiver; an `AGENT` (command-verified) check is waivable only when the controller passes the identical record in `recorded_waivers`, and when `recorded_waivers` is supplied every waiver must match its entry. SPECIFY through TASKS and future slices still require `PLANNED`. A `required_commands` entry bound only to waived checks is not demanded. Waiver rejections carry `next_step` (`WAIVER_NEXT_STEP`) and `next_command` (`WAIVER_NEXT_COMMAND`). A role approval (product owner, tech lead) named in a request is a HUMAN check, never a gate that blocks IMPLEMENT unless the request literally says so.

Workers are dispatched only through [`executor_launch.py run`](#executor_launchpy-and-executorsmd); the controller never writes a `claude` or `codex` command line.

**Write scope and evidence citations.** SPECIFY, CLARIFY, PLAN, TASKS and TEST are analysis-only, so any reported `modified_paths`/`created_paths` is rejected. IMPLEMENT must receive controller-declared `editable_paths` for every status. Each pattern must be anchored and not match-all (`editable_pattern_is_safe`). Every written path (and every pattern) must be repository-relative, non-traversing, without a segment starting with `-` (it would become an option when gates expand `{files}`), and matched segment by segment by one of them (`path_matches`; `*` does not cross `/`). A current-slice (IMPLEMENT) or TEST `PASS` from an `AGENT` verifier must cite, in backticks, one of the commands the controller bound to that check (`check_verifiers`), and that command must be recorded as exit `0` with `PASS` or be the GREEN command. "Done", a self-chosen command or another check's verifier is not evidence. **Read-only roles.** With `role` set to one of `READ_ONLY_ROLES` (`PROJECT_CONTEXT_GUARDIAN`, `DATA_FLOW_TRACER`) and only in that role's declared stages, a result reports no writes and no TDD slices. `DATA_FLOW_TRACER` is allowed in SPECIFY, CLARIFY, PLAN, TASKS and IMPLEMENT, `PROJECT_CONTEXT_GUARDIAN` in SPECIFY, PLAN and IMPLEMENT. It keeps unverified checks `PLANNED` without evidence and carries completed-slice checks forward as `PASS` (or `WAIVED`) with evidence. The editable-path, TDD and citation requirements do not apply to it. With `required_commands`, a successful IMPLEMENT/TEST must record each required verifier as passing.

**TDD evidence.** `IMPLEMENT` with status `SUCCESS` needs at least one slice with a non-zero RED exit, `red_failure_kind: EXPECTED_FUNCTIONAL`, and GREEN exit `0`. An infrastructure failure does not count as RED.

**Acceptance.** A non-zero CLI exit is a process failure. A zero exit with invalid JSON is `CONTRACT_INVALID`. Cited paths and symbols, ownership and TDD evidence are checked against the repository before a transition. A valid envelope is not proof that its commands actually ran.

## Review result

Used by `REVIEW` and the audit sub-agents. The root is `review_result`, with these fields: `status` (`APPROVED`, `CHANGES_REQUIRED`, `BLOCKED`), `reviewed_paths`, `findings` (severity, path, description, evidence), `baseline`, `ownership`, `acceptance` (`expected_check_ids`, independent verification and ID-matched evidence-backed checks), `e2e` (`files_modified`, `execution_performed` and `violation` are kept separate), `forbidden_actions`, `gate_status` and `next_step`.

`APPROVED` requires the controller's authoritative acceptance mapping, exact ID and criterion coverage with evidence and every check `PASS` or `WAIVED`, a preserved baseline with no violations, valid ownership with no violations, no unresolved findings and `focused_tests`/`format`/`analyze` at `PASS`. Baseline and ownership booleans must agree with their violation arrays for every review status. Green technical gates do not substitute for checking the accepted observable outcomes. Gate values are defined in [Gates](gates-and-stack-detection.md#gate-order-gatesmd). The reviewer is read-only and cannot declare DONE.

## `executor_launch.py` and `EXECUTORS.md`

`runtime/executor_launch.py` is the only way to start a worker. Every executor-specific step is looked up by executor name in `runtime/executor_dispatch.py` — `EXECUTORS`, the `--help` probe argv (`HELP_ARGS`), `REQUIRED_HELP_FLAGS`, the argv builder and the side files written before the process starts (`BUILDERS`, `launch_plan`) and whether a stage writes (`is_writing_worker`) — and in `executor_transport.EXTRACTORS` for the final message (OpenCode's stream is read by `runtime/opencode_transport.py` instead); nothing falls back to Codex, and an executor that is not in `EXECUTORS` is `POLICY_INVALID`. Final-message extraction is in `runtime/executor_transport.py` and the sandbox probe plus per-stage Codex settings helpers in `runtime/executor_sandbox.py`. It reads `policies/EXECUTORS.md`, a project-owned file with one fenced JSON block (`executors_version: 1`, `stages: {STAGE: {executor, model, timeout_seconds, max_turns}}`, optional `tools`, `permission_mode`, `sandbox`, `sandbox_network`, `codex_home`, `env_from`, `prompt_profile` (`standard`, the default, or `compact`), and the top-level owner flags `workspace_audit` (`off`, the default, or `enforce`; see [Workspace audit](#workspace-audit-opt-in)) and `allow_bypass_permissions`, default `false`; `permission_mode: bypassPermissions` without it is `EXECUTOR_POLICY_UNSAFE`). Defaults, also used when the file is absent: `SPECIFY`, `CLARIFY`, `PLAN` and `REVIEW` on `claude`; `TASKS`, `IMPLEMENT` and `TEST` on `codex`; `timeout_seconds` 900 for PLAN and IMPLEMENT, 600 otherwise; `model: null` (CLI default). A stage omitted from the block keeps its default; an invalid block is `POLICY_INVALID` (`POLICY_SOURCES`: `FILE`, `DEFAULTS`).

```text
executor_launch.py schema --stage REVIEW [--role SECURITY_REVIEWER]
executor_launch.py preflight --executor claude|codex|opencode [--model M] [--stage S] [--probe] [--probe-sandbox]
executor_launch.py build --stage S --prompt-file P --journal J --final F [--executor E] [--model M] [--timeout SEC] [--role R] [--repo DIR] [--add-dir DIR] [--read-dir DIR] [--policy FILE]
executor_launch.py run   (same flags as build)
```

- `schema` prints the **transport schema**: the stage's result schema (`REVIEW_RESULT_SCHEMA.json` for REVIEW, the role brief's `result_schema` with `--role`) without `$schema`, `$id` and `$comment`, with local `$ref`s inlined and `$defs` dropped. The Claude CLI rejects `--json-schema` with a draft 2020-12 `$schema` reference; the transport schema validates exactly like the source for Draft 2020-12 and Draft 7. An external or recursive `$ref` is `SCHEMA_UNSUPPORTED`; a role not allowed in the stage is `ROLE_UNKNOWN`.
- `preflight` checks that the CLI is on PATH, that `--version` runs and that its help lists the flags the launcher uses (for Claude this includes the isolation flags `--setting-sources`, `--strict-mcp-config` and `--disable-slash-commands`; a CLI without them is `EXECUTOR_CLI_UNSUPPORTED` and `next_step` names the missing flags); it makes no model call. `--probe` adds one minimal real call that proves login and model. `--stage S` loads that stage's settings from `policies/EXECUTORS.md` (including `model`, `codex_home`, `env_from` and `sandbox_network`) and the `--probe` call runs with that stage's worker environment; a missing `codex_home` directory is `BLOCKED` with `CODEX_HOME_INVALID` and a missing `env_from` variable is `BLOCKED` with `EXECUTOR_ENV_MISSING`, both before the probe. `--probe-sandbox` requires `--stage` and runs, for Codex with `workspace-write`, the three probes through `codex sandbox` (TCP listen on `127.0.0.1:0`, Unix-socket listen in a fresh temp dir, `docker info`) without a model call, and reports `sandbox_probe: {tcp_listen, unix_listen, docker, network_access}` where each probe is `OK`, `BLOCKED`, `SKIPPED`, `ERROR` or `UNSUPPORTED` (`SKIPPED` when a binary is not on PATH; the Docker probe first runs an unsandboxed `docker info` baseline with the same short timeout and is `SKIPPED` when that fails, `BLOCKED` only when the baseline succeeds and the sandboxed run fails; before probing, `codex sandbox --help` must list `-c`/`--config` or every probe is `UNSUPPORTED` with no warning) plus advisory `warnings` (`SANDBOX_NETWORK_ENABLED` when the stage sets `sandbox_network`; `SANDBOX_NETWORK_REQUIRED` with a `next_step` when a probe is `BLOCKED` and the stage does not set `sandbox_network`). Result `READY` or `BLOCKED` with `reason` (`PREFLIGHT_REASONS`: `EXECUTOR_UNAVAILABLE`, `EXECUTOR_CLI_UNSUPPORTED`, `MODEL_INVALID`, `MODEL_REJECTED`, `CODEX_HOME_INVALID`, `EXECUTOR_ENV_MISSING`) and `model_check` (`MODEL_CHECKS`: `NOT_PROBED`, `ACCEPTED`, `REJECTED`, `TIMEOUT`).
- `build` prints the exact argv, working directory, stdin file and timeout that `run` would use, without touching the journal.
- Extra directories. A *writing worker* is Codex with `workspace-write` or Claude whose `tools` include anything beyond `Read`, `Grep`, `Glob`, `LS`, `NotebookRead` (or `default`). `--add-dir` is writable for both, so for a writing worker it must lie inside the repository and outside the controller's `.hermes` directory; otherwise `build`/`run` refuse with `ADD_DIR_WRITABLE_REFUSED` before anything is dispatched. `--read-dir` names a directory the worker only reads: a read-only Claude worker receives it as `--add-dir`, Codex ignores it (both sandboxes read the filesystem), and a writing Claude worker is refused. `sdd.py` passes the Obsidian controller container only as `--read-dir`, so in Obsidian storage no worker *process* can edit `GATES.md`, `EXECUTORS.md`, STATE or the journal. Code that worker writes into the repository can, once a gate executes it: gates run on the host with the user's privileges (see [Gates](gates-and-stack-detection.md#gate-order-gatesmd)), so they belong in a trusted environment and REVIEW reads the diff of test, fixture, build and tool-configuration files. The [workspace audit](#test-run-artifacts) does not help here for bytecode caches: it leaves out a `__pycache__/*.pyc` whose header matches its source, so a crafted one is not reported. `sdd.py gate` does not load it, because every gate command runs with a fresh `PYTHONPYCACHEPREFIX` and `PYTHONDONTWRITEBYTECODE=1` (`runtime/gate_env.py`), but any other Python that loads the repository's cache runs it.
- Controller isolation. A writing worker is never dispatched while the controller lives inside its writable repository: `build`/`run` refuse with `CONTROLLER_WRITABLE_BY_WORKER` and `sdd.py next` stops with the same code before preparing the action and on the recovery DISPATCH path for an already PREPARED action, printing `exit_commands` (`sdd.py abandon` → `install_project.py --obsidian-vault <vault> --obsidian-project <project>` dry run then `--apply` → move of the in-repository controller → `confirm-policy` → `sdd.py start`); the criterion is the controller's physical location, not the storage label. `migrate_to_vault.py` is not the exit: it keeps `runtime/*.py` and `policies/` in the repository by design; the exit is `sdd.py abandon`, reinstall in Obsidian mode, then start again. This is prevention, not detection: such a worker can rewrite `GATES.md`, `EXECUTORS.md`, `runtime/*.py`, the briefs, STATE and the journal *together with* every hash they would be checked against, since each anchor lives in the same writable tree — so a tamper check there has nothing the worker cannot reach. Read-only stages (SPECIFY, CLARIFY, PLAN, TASKS, REVIEW) still run under `--local-storage`; only Obsidian storage runs a writing worker. The tamper checks remain as defence in depth: `start` pins the SHA-256 of `GATES.md` and `EXECUTORS.md` in `delivery.controller_policies`, every `gate` re-verifies both (`CONTROLLER_POLICY_CHANGED_DURING_DEMAND`, or `CONTROLLER_POLICY_UNPINNED` with no pin at all) and only `sdd.py confirm-policy --name gates|executors --quote '<user words>'` re-pins one of them; a file that cannot be hashed at all stops with `CONTROLLER_POLICY_UNREADABLE`, which prints `sdd.py restore-policy --name <policy> --skill <installed-skill>` plus `confirm-policy` rather than a confirmation (pinning the empty digest would loop; Git cannot restore a file in the vault or in an excluded `.hermes/`). `sdd.py next` raises both policy stops before printing any `gate` command, so the controller never runs a batch that can only refuse. `accept` likewise refuses a STATE changed outside the journal's commit (`STATE_MODIFIED_DURING_ACTION`), and `next` stops with it too; its exit is `sdd.py abandon`, which archives the open action as evidence and returns STATE to IDLE so the demand can be re-run.
- `run` performs one journaled dispatch:
  1. refuses before any process starts unless `action_journal.py recover` is `DISPATCH_ALLOWED` (`DISPATCH_NOT_ALLOWED`), the journal is `PREPARED` (`JOURNAL_NOT_PREPARED`) for the same stage, final path and executor (`JOURNAL_MISMATCH`), the prompt file's SHA-256 equals `prompt_hash` (`PROMPT_HASH_MISMATCH`), and no final-message file exists (`ARTIFACT_PENDING`). Other refusals: `EXECUTOR_UNAVAILABLE`, `EXECUTOR_ENV_MISSING`, `PROMPT_MISSING`, `REPOSITORY_INVALID`, `STAGE_UNKNOWN`;
  2. calls `record-process --started` (adding `--prompt-sha256 <hex>` when the journal CLI supports it); a refusal is `JOURNAL_REFUSED` and nothing runs;
  3. runs the CLI **in the foreground**, without a shell, with the journal's `workspace.path` (or `--repo`) as working directory, the prompt on stdin, an allow-listed environment and a hard timeout. The environment keeps only `PATH`, `HOME`, `LANG`, `LC_*`, `TMPDIR`, `USER`, `LOGNAME`, `SHELL`, `TERM`, `TZ`, `XDG_*` directories, certificate and proxy variables, plus the executor's own `ANTHROPIC_*`/`CLAUDE_*` or `OPENAI_*`/`CODEX_*`; for a Codex stage, `codex_home` sets `CODEX_HOME` and `env_from` allowlists up to 4 controller variables (a missing one is `EXECUTOR_ENV_MISSING` before any journal write). `TYPESAFE_*`, `JEV_*`, `HERMES_*` and other `*_API_KEY`/`*_TOKEN` never reach the worker, and `env_from` values are never written to argv, results or the journal (`preflight --probe` uses the same environment); `stderr_tail` is the worker's own stderr and is not filtered. On timeout it sends SIGTERM then SIGKILL to the whole process group. A SIGTERM or SIGHUP to the launcher becomes `LAUNCHER_INTERRUPTED`: the group is killed the same way and exit `125` is recorded. A grandchild that calls `setsid` leaves the group and is not killed. Directories outside the repository are never the working directory;
  4. **always** calls `record-process --finished --exit-code N` in a `finally` block, with SIGTERM/SIGHUP blocked while the journal is written: the CLI exit code, `124` on timeout, `125` when the launcher itself fails or is interrupted, `127` when the binary cannot be executed. A failure here is `JOURNAL_FINISH_FAILED`;
  5. extracts the final message — Claude: `structured_output` of the `--output-format json` envelope (falling back to the textual `result`); Codex: the `--output-last-message` file, with a strict-but-tolerant transport that accepts, only when the last message is not already one JSON object, exactly one fenced block (` ```json ` or ` ``` `) whose content parses as a JSON object (`transport_source: FENCED_BLOCK`), or exactly one top-level JSON object with nothing else that parses as JSON (`transport_source: SINGLE_OBJECT`); two fenced blocks, two top-level objects, a non-object block or prose without a block stay invalid. The normalized object is written atomically to `--final` and the raw message is kept beside it as `<final>.raw-message.txt`; `transport_normalized: true` is merged into the launch result. The journal contract does not change: the record stays the launcher's JSON result (which the controller logs) plus the sidecar file. `validate_protocol.py` still runs afterwards, unchanged — only the transport is tolerant. It writes `--final` atomically and calls `record-artifact`.

  Claude argv: `claude -p --output-format json --json-schema <transport> --no-session-persistence --setting-sources user --strict-mcp-config --disable-slash-commands --tools <tools, default Read,Grep,Glob> [--max-turns N] [--model M] [--permission-mode P] [--add-dir D]`. Codex argv: `codex exec --ephemeral --color never --cd <repository> --sandbox <read-only|workspace-write> --output-schema <final>.transport-schema.json --output-last-message <final>.last-message.tmp [--model M] [--config sandbox_workspace_write.writable_roots=[]] [--add-dir D] -` (`--config` for `workspace-write`; `preflight` requires `--config` in the help); the sandbox defaults to `workspace-write` for IMPLEMENT and TEST and `read-only` otherwise. The temporary transport-schema file is always removed. The three Claude isolation flags (also on the `--probe` call) keep the repository's `.claude/settings.json`/`settings.local.json` hooks, `.mcp.json` servers and `.claude/skills` from loading: `-p` skips the workspace-trust dialog, and those files are ones a writing worker can create for the next stage. `--bare` is not used because it disables OAuth/keychain login. Codex `exec` has no flag that ignores a project `.codex/` directory; with codex-cli 0.160.0 its `config.toml` and `hooks.json` did not run in an untrusted repository, and the residual risk (other versions, a repository the user marked trusted) is stated in `policies/EXECUTORS.md`. Containment checks (`--add-dir`, controller isolation) compare paths by `(st_dev, st_ino)` along the ancestors, so a case-flipped alias on a case-insensitive filesystem is still recognised as inside the repository or the controller.

`run` prints `{status, exit_code, final, executor, stage, duration_seconds, stderr_tail, next_step, next_command}` plus, when transport normalization happened, `transport_normalized` and `transport_source`. For a Claude worker it also adds `usage` when the CLI envelope reports one (`executor_transport.envelope_usage`): `MEASURED` input, output, cache-read and cache-write tokens, the CLI's `cost_usd` (a finite, non-negative number, else `null`), `duration_api_ms` and `num_turns`, with any missing counter as `null`; nothing stores this output yet ([Observability](observability.md)). Statuses (`LAUNCH_STATUSES`):

| Status | Meaning | `next_command` |
| --- | --- | --- |
| `ARTIFACT_READY` | Final message is a JSON object; journal `ARTIFACT_READY`. | `validate_protocol.py --action <STAGE> --result <final> --context <verifier-context.json> --json` |
| `OUTPUT_INVALID` | Exit 0 but the final message is not a JSON object; kept as evidence, journal `ARTIFACT_READY` (`CONTRACT_INVALID`). | `action_journal.py ... classify-invalid --invalid-field <field>` |
| `EXECUTOR_TIMEOUT` | Hard timeout; process group killed; exit `124` recorded. | `action_journal.py ... archive-interrupted --history-dir <journal dir>/action-journal-history` |
| `EXECUTOR_FAILED` | Non-zero exit recorded. | same archive command |
| `EXECUTOR_NO_OUTPUT` | Exit 0 without any final message. | same archive command |
| `LAUNCHER_ERROR` | The launcher failed after `--started`; exit `125`/`127` recorded. | same archive command |
| `LAUNCHER_INTERRUPTED` | SIGTERM/SIGHUP to the launcher; process group killed, exit `125` recorded, `signal` reported. | same archive command |
| `JOURNAL_FINISH_FAILED` | `--finished` or `record-artifact` was refused. | `action_journal.py ... inspect` |

### OpenCode worker

`opencode` is an optional executor: no stage uses it unless `policies/EXECUTORS.md` says so, and the shipped defaults never do. `runtime/opencode_executor.py` builds it and `runtime/opencode_transport.py` reads its output.

- **Version pin.** `preflight --executor opencode` requires `opencode --version` to be exactly `PINNED_VERSION` (`1.18.34`); anything else is `BLOCKED` with `EXECUTOR_CLI_UNSUPPORTED` and a `next_step` naming the pinned version. It also requires the codex CLI with `sandbox -c/--config` and an existing OpenCode data directory, otherwise `EXECUTOR_UNAVAILABLE`, and a `provider/model` value, otherwise `MODEL_INVALID`.
- **Argv.** `codex sandbox -c sandbox_mode="workspace-write" -c sandbox_workspace_write.network_access=true -c sandbox_workspace_write.exclude_slash_tmp=true -c sandbox_workspace_write.exclude_tmpdir_env_var=true -c sandbox_workspace_write.writable_roots=["<data dir>"] -- opencode run --format json --pure --auto --dir <repository> -m <model> -f <final>.transport-schema.json`. The working directory is the repository for a writing stage and `<data dir>/sdd-runtime/<dispatch>/work` for a read-only one, since the Codex read-only sandbox mode cannot add a writable root. `--add-dir` is refused (`ADD_DIR_WRITABLE_REFUSED`).
- **Hermetic environment** (`HERMETIC_ENV`): `OPENCODE_PURE` plus the project-config, external-skill, Claude Code (prompt and skills), default-plugin, autoupdate, share and LSP-download disables, per-dispatch `XDG_CONFIG_HOME`/`XDG_CACHE_HOME`/`XDG_STATE_HOME`/`TMPDIR` under `<data dir>/sdd-runtime/<dispatch>/`, and an `OPENCODE_PERMISSION` (`opencode_executor.permission`) that denies `DENIED_TOOLS` (`webfetch`, `websearch`, `codesearch`, `task`) and every `external_directory`, allows reading only the `--read-dir` paths while denying `edit` on them, and denies `edit` outside the workspace and in `.git`; a read-only stage denies `edit` everywhere. The `read` tool is denied on `CREDENTIAL_READ_DENY` (`*opencode/auth.json`, `*opencode/opencode.db*`) and `bash` on any command matching `CREDENTIAL_BASH_DENY` (`*auth.json*`, `*opencode.db*`). Verified on 1.18.34: `read` patterns match the path relative to the project (an absolute pattern never matches, hence the globs ending in the data directory's name), `external_directory: deny` already refuses the `read` tool outside the project, and `bash` patterns match the command text. These rules are defence in depth, not a boundary: the seatbelt must let the process read OpenCode's data directory, so a command that never names the file could still reach it, which is why the stored stream drops every tool part. Rules are always `deny`, never `ask`. `DROPPED_ENV` (`OPENCODE_API_KEY`, `OPENCODE_CONSOLE_TOKEN`, `OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR`, `OPENCODE_CONFIG_CONTENT`, `OPENCODE_PERMISSION`, `OPENCODE_SERVER_PASSWORD`, `OPENCODE_SERVER_USERNAME`) plus any `OPENCODE_*` name ending in `_KEY`/`_TOKEN`/`_SECRET`/`_PASSWORD` is removed from the inherited environment. `build`/`run` report `executor_version`, `model` and `opencode_config_sha256` (SHA-256 of the effective hermetic environment and permission JSON).
- **Output** (`opencode_transport.classify`): exactly one final text in the last step, whose `step_finish` reason must be `FINISH_REASON` (`stop`). `OUTCOMES` (`OK`, `INVALID_OUTPUT`, `PARTIAL`, `TIMEOUT`, `CRASH`, `ERROR_EVENT`) map through `OUTCOME_STATUS` onto `ARTIFACT_READY`, `OUTPUT_INVALID`, `EXECUTOR_NO_OUTPUT`, `EXECUTOR_TIMEOUT` and `EXECUTOR_FAILED`, and `opencode_outcome` is reported. `usage` sums the `step_finish` token counters and costs (`MEASURED`). The stored raw stream `<final>.raw-stream.jsonl` keeps only the `RAW_STREAM_EVENTS` (`step_start`, `text`, `step_finish`, `error`) lines (`opencode_transport.raw_stream`), so no `tool_use` part — what a tool read, its input or metadata — is ever written, and passes through `redaction.redact()`, as do `stderr_tail` and the model probe's `probe_stderr_tail`. `redact()` also masks token-shaped values of the bare JSON keys `key`, `refresh` and `access` (OpenCode's `auth.json` shape), including the JSON-escaped form inside a JSONL line. The result then goes through the same transport schema and `validate_protocol.py` as every other executor.
- **State.** OpenCode's data directory (`$XDG_DATA_HOME/opencode`, default `~/.local/share/opencode`) holds the logged-in account and is used in place; nothing is copied or exported from it. The per-dispatch directory (`RUNTIME_FOLDER` = `sdd-runtime`) is created before the process and deleted afterwards. Sandbox network access is always on for OpenCode: the seatbelt switch is all-or-nothing and the provider is remote.

Refusals before dispatch also include `ADD_DIR_WRITABLE_REFUSED` and, from policy loading, `EXECUTOR_POLICY_UNSAFE`. Every refusal status above carries a `next_step`, and a `next_command` when one exists. `READY` (from `preflight`/`build`) and `ARTIFACT_READY` exit `0`; everything else exits `2`. Its behavior is pinned by `tests/test_executor_launch.py` with fake `claude`/`codex` executables on a temporary PATH ([Testing](testing.md#installed-controller-tests)).

## Workspace audit (opt-in)

`runtime/dispatch_audit.py` is an independent check of one writing dispatch, off unless the project sets `"workspace_audit": "enforce"` in `policies/EXECUTORS.md` (`MODES`: `off`, `enforce`; `DEFAULT_MODE` is `off`). With the default, the controller behaves exactly as before for every executor and none of this runs.

When it is enabled, `sdd.py prepare` (`workspace_audit_prepare`) writes `snapshot(repo, exclude)` to `<action>.workspace-before.json` and records `{action_id, key, mode: "enforce", baseline_action_id}` in `delivery.workspace_audit`; `validation_step`/`accept` (`workspace_audit_stop`) call `audit(...)` afterwards. The mode recorded at `prepare` wins over the policy: switching the audit off in `EXECUTORS.md` mid-dispatch does not skip it. A corrective retry of the same action series (same `key`) keeps the series' first baseline (`prepare_record`), so a file a failed attempt left behind is still reported; a new series takes a fresh one.

The snapshot (`SCHEMA_VERSION` 3; an older baseline is `AUDIT_UNVERIFIABLE`) records every dirty, untracked **and ignored** path (`git status --porcelain -z --untracked-files=all --ignored`, both halves of a rename) with its content hash, size and executable bit; `HEAD`; a hash of every ref and the symbolic `HEAD`; a hash of the index entries with their flags (`git ls-files -s -v`, so `--skip-worktree`/`--assume-unchanged` count; `git write-tree` is not used because it writes objects); the hash of every `.gitignore`, of `.git/info/exclude` and of `core.excludesFile` (`ignore_rules`); `diff_sha256`, one hash of `git diff --binary --no-ext-diff --no-textconv HEAD`, `--cached` and the unstaged diff; `git_dir`, the absolute Git directory; `config_sha256`, a hash of `git config --list -z --show-origin --includes` (every setting with its origin file, so an `[include]`/`[includeIf]` target or its contents count); and `hooks_sha256`, a hash of every entry of the effective hooks directory (`git rev-parse --git-path hooks`, which follows `core.hooksPath`) and of `<git-dir>/hooks`. Every `git` call runs as `git -C <repo> --git-dir <git_dir> --work-tree <repo>`, with the `git_dir` recorded at `prepare` reused for the after-snapshot, and overrides with `-c` the settings a worker that can write `.git/config` could use to change what status, diff and ls-files report (`_OVERRIDES`: `core.worktree=`, `core.bare=false`, `core.fsmonitor=false`, `core.untrackedCache=false`, `status.showUntrackedFiles=all`); a redirection to a shadow work tree therefore cannot hide the real files, and the config, hooks or Git-directory change itself is `GIT_STATE_MOVED` with the path `config`, `hooks` or `git_dir`. `changed_paths` lists the paths whose status or content differs, so a silent rewrite, a revert, a mode change and staged work all count. The only paths left out are the controller's own files when they physically live in the repository (`exclusions`: the orchestration folder, runtime directory, STATE, journal and history) and the [test-run artifacts](#test-run-artifacts) below; every other ignored file counts.

### Test-run artifacts

Running a project's tests rewrites its runner cache, coverage data and bytecode caches on every run, and running its type checker and linter rewrites theirs. Before this list, each was an `UNDECLARED_CHANGE` and every IMPLEMENT/TEST slice that ran the tests stopped. `runtime/audit_scope.py` now leaves out exactly these paths, and only while they are untracked and git-ignored — and, for a path the dispatch deleted, only when the **baseline** had it git-ignored. The names are `TEST_RUN_ARTIFACT_TREES` (`TEST_RUNNER_ARTIFACT_TREES` plus `GATE_CACHE_TREES`), `TEST_RUN_ARTIFACT_FILES`, `TEST_RUN_ARTIFACT_PREFIXES`, `TEST_RUN_ARTIFACT_CODE_SUFFIXES`, `BYTECODE_CACHE_DIR`, `BYTECODE_SOURCE_SUFFIX` and `BYTECODE_NAME` in `runtime/detect_stack.py`, the only module that may name toolchains.

| Rule | Why |
| --- | --- |
| `.pytest_cache/` at the root, when the baseline's rules ignored that directory from **outside** the tree, whole subtree except files ending `.py`, `.pyc`, `.pyo`, `.pth`, `.so`, `.pyw`, `.pyd`, `.pyz`, `.dylib`, `.egg-link` | The test runner rewrites `v/cache/nodeids`, `lastfailed` and its own `.gitignore` on every run. It never runs code from there, so code suffixes still count. |
| `coverage.xml`, `.coverage`, `.coverage.*` at the root, same code-suffix rule | Coverage data written by every covered run (`.coverage.*` are the parallel-mode files; `.coveragerc` does not match). |
| `htmlcov/` at the root, same outside-the-tree and code-suffix rules | The coverage HTML report. |
| `.mypy_cache/` and `.ruff_cache/` at the root, same outside-the-tree and code-suffix rules | The type checker's and linter's incremental caches (`cache.N.db`, `<version>/<hash>`), which a worker that runs those tools rewrites every time (FP-006 slice S7 was stopped by 29 such findings). They are safe to leave out only because no gate reads them: `sdd.py gate` and the validation gates give every gate run fresh `MYPY_CACHE_DIR`/`RUFF_CACHE_DIR` directories ([Gates](gates-and-stack-detection.md#gate-order-gatesmd)), so a cache planted here cannot hide an error from a gate. Neither tool executes anything from its cache, and code suffixes still count. |
| `<dir>/__pycache__/<stem>.<tag>[-pytest-<version>][.opt-1\|.opt-2].pyc`, at any depth | Bytecode the interpreter and the test runner's assertion rewriting write next to every imported module. It is left out only when `<dir>/<stem>.py` exists, the entry is a regular file and its 16-byte header is timestamp-based (flags `0`) and records exactly that source's mtime (seconds, modulo 2**32) and size. |

The filter runs at compare time, on both snapshots. `snapshot` still records every path in `files` and adds three fields: `status`, each listed path's two-letter `git status` code (`!!` is untracked and ignored, `??` untracked and not ignored); `artifact_roots`, the artifact tree roots an ignore rule **outside** the tree covers (`git check-ignore -v -z --stdin --no-index`, so a `.pytest_cache/.gitignore` holding `*` that the worker wrote neither makes the subtree eligible nor hides its own change, which is `IGNORE_RULES_CHANGED`); `artifact_trees`, the tree roots this snapshot evaluated; and `test_artifacts`, the artifacts it found. The after-snapshot gets the baseline (`snapshot(..., baseline=before)`), uses the **baseline's** `artifact_roots` (`audit_scope.baseline_roots`), and can mark a baseline path that is now gone from `git status` and from disk only when the baseline's `status` had it `!!` — so an untracked, unignored `coverage.xml`, `htmlcov/x.html` or `.pytest_cache/x` the dispatch deleted is still `UNDECLARED_CHANGE`. `changed_paths` and `audit` then skip `audit_scope.skipped(before, after)` in `files` and `ignore_rules` alike. A baseline stored by 15.19.0 has neither field: its removed paths are resolved with `git check-ignore -z --stdin --no-index` against the pinned Git directory, that is with the **current** rules, the only ones available (a rule the dispatch added is reported separately as `IGNORE_RULES_CHANGED`), and the roots fall back to the current rules too. A baseline stored by 15.19.1 has `artifact_roots` but no `artifact_trees`: it evaluated only `.pytest_cache` and `htmlcov`, so its roots decide those two, while `.mypy_cache`/`.ruff_cache` are decided by the current `git check-ignore -v` answer **only** when every ignore rule outside the artifact trees (`ignore_rules` minus the entries inside a tree) is unchanged since the baseline, which makes the current answer the one the baseline's rules gave; a rule inside a tree never decides whether that tree is ignored. A changed rule leaves those trees out and is itself `IGNORE_RULES_CHANGED`. An FP-006 baseline therefore keeps passing after an upgrade, because the project's `.gitignore` ignores those caches and did not change, and an open action stopped by 15.19.1 for gate-cache findings only is accepted when `sdd.py next` re-audits it. `SCHEMA_VERSION` stays 3.

Everything else still counts. That includes a tracked or unignored file with one of these names, the same names below the root, an undeclared source or document, a `.pyc` outside `__pycache__/`, any other file inside `__pycache__/`, a `.pyc` with no sibling source or an unknown name, a hash-based `.pyc` (flags `1`/`3`: checking it needs the project's interpreter, so it is reported), a header that does not match its source, a symlink, a `conftest.py` anywhere, a changed ignore rule outside an ignored artifact tree, the same caches below the root (`sub/.mypy_cache/`), and a deleted artifact-named file the baseline did not have git-ignored. They are pinned by `tests/test_dispatch_audit_test_artifacts.py`, `tests/test_dispatch_audit_artifact_status.py` and `tests/test_dispatch_audit_gate_caches.py`.

Each changed path must appear in the result's `modified_paths`/`created_paths` (`declared_paths`) and, for `IMPLEMENT`, match the slice's `editable_paths` through the validator's own `path_matches`. The `FINDINGS` are `UNDECLARED_CHANGE`, `OUTSIDE_EDITABLE_PATHS`, `IGNORE_RULES_CHANGED` (any ignore rule changed, even when declared, since it could hide files), `GIT_STATE_MOVED` (`HEAD`, `refs` or `index` moved — a worker never commits or stages —, the Git directory, configuration or hooks changed, or the diff hash moved although no listed file did) and `AUDIT_UNVERIFIABLE`. The audit fails closed: every `git` call is checked (`AuditError` on a non-zero exit or a timeout), and a missing or corrupt baseline, an unreadable result or a failing `git` call is `AUDIT_UNVERIFIABLE`, never a pass; a baseline that cannot be taken refuses `prepare` with the same stop. One or more findings stop the loop with `STOP_REASON` = `WORKSPACE_AUDIT_FAILED` (registered in [the stop-reason registry](fsm-and-loop.md#stop-reasons-stop_reasonspy)) and the result is never folded into STATE. `AUDITED_STAGES` is `IMPLEMENT` and `TEST`; a read-only stage is never audited. The audit applies to `claude`, `codex` and `opencode` identically — the declared paths of any executor are checked against the repository rather than trusted. Nothing is reverted automatically: the stop asks the user to decide and then `sdd.py abandon` or reopen the slice. It is pinned by `tests/test_dispatch_audit.py` and, for every bypass found in review and the fail-closed paths, `tests/test_dispatch_audit_bypasses.py`.

**Known limits** (not enforced; changing them needs an owner decision): (1) an embedded Git repository or submodule that already existed before the dispatch is not inspected inside — `git status` lists it as one directory entry (hashed as `directory`) or as a `-dirty` gitlink — so edits within it go unseen, while a newly created one is reported; (2) `_hash` reads at most about 8 MiB of a file and records that prefix digest plus the size and executable bit, so a same-size edit past the first 8 MiB of an untracked or ignored file is not seen, and `diff_sha256` (which covers tracked content in full) is consulted only when nothing else changed; (3) the snapshot hashes every ignored file (`node_modules`, `.venv`, build output), which can be slow on large repositories — each `git` call times out fail-closed at 120 s, but the hashing loop itself has no time budget; (4) a crafted timestamp-based `.pyc` whose header copies its source's mtime and size is left out like a real one. A writing worker can build one, since it can read both values and can also set the source's mtime. The audit then does not see it. `sdd.py gate` does not load it: every gate command runs with a fresh, per-run `PYTHONPYCACHEPREFIX` outside the repository and `PYTHONDONTWRITEBYTECODE=1` ([Gates](gates-and-stack-detection.md#gate-order-gatesmd)). Any **other** Python that loads the repository's `__pycache__/` runs it instead of the source: the user's own test run, an IDE, `python -I`, or a gate command that clears those variables itself. The header check rejects stale, orphan and hash-based files only. It does not check the content.

## `validate_protocol.py`

Validates a final-message JSON against the selected schema plus semantic rules (envelope/action match, material-context resolution, authoritative acceptance mapping, controller-selected current/completed slices, write scope, evidence citations, required verification, TDD evidence and path shapes). `validate_payload` and `validate_json_text` accept `expected_acceptance`, `current_slice_ids`, `completed_slice_ids`, `editable_paths`, `required_commands`, `check_verifiers`, `role`, `recorded_waivers` and `validate_impact_files`. TASKS always validates `stage_payload.impact_files` as safe editable patterns; the controller sets `validate_impact_files: true` for a DECISION_DOC PLAN so that PLAN is refused before it can be folded, while a CODE PLAN remains unaffected. A trailing directory slash is normalized to `/**` for that check; other entries are unchanged. `ANALYSIS_ONLY_ACTIONS` lists the stages that may not report file changes; every IMPLEMENT, TEST and REVIEW status fails closed unless both the authoritative acceptance mapping and returned check set are present and non-empty, and IMPLEMENT success additionally requires controller-owned current/completed slice inputs. The module never executes commands in the payload and never reads STATE.

```text
validate_protocol.py --action IMPLEMENT --result final-message.json --context verifier-context.json --json
```

Flags: `--action`, `--result`, `--context`, `--json`. `--context` takes the output of [`stage_context.py verifier-context`](harness.md#feeding-the-validator). Unknown keys or a value of the wrong type (for example `check_verifiers` given as a list) are rejected as structured errors. Exit `0` means valid; `2` means the result or the context is rejected and the errors are listed. Its behavior is pinned by `tests/test_protocol.py` ([Testing](testing.md#installed-controller-tests)).

Changing a schema is a contract change: bump the `SKILL.md` version and update this page, the example envelopes in both contracts, and `test_protocol.py`.

`runtime/protocol_read_only.py` holds the pure read-only-role acceptance/TDD checks called by `validate_protocol.py`; the validator keeps the public API and documented error semantics.
